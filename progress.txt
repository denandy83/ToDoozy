## Story #92 — Batch task-detail edits (2026-06-10)

New `TaskBatchSyncManager.ts`: module-level `pendingTaskIds` Set + per-task 30s safety timers. While a task
is open in the Detail panel, `taskStore.updateTask` / `addLabel` / `removeLabel` call `markPending(taskId)`
instead of pushing; `flush(taskId)` re-reads the task from the store and pushes through the SAME
`syncIfShared` routing (now exported from taskStore) so shared/personal both work. `flush` is a no-op when
not pending (double-flush safe) and skips tasks deleted while buffered.

Boundaries wired:
- Task switch: `selectTask`/`navigateTask`/`setCurrentTask(id)` flush the previous lastSelectedTaskId.
- Panel close: `setCurrentTask(null)` + `clearSelection` flushAll; DetailPanel's Escape handler (which
  bypasses store actions with a raw setState) flushes explicitly.
- App blur: window 'blur' listener in App.tsx.
- Quit: main intercepts the FIRST before-quit (preventDefault), sends `app:before-quit-flush` to all
  windows, renderer flushes and acks via `app:before-quit-flush-done`, main quits on ack or 1.5s timeout
  (sync_queue/reconcile covers anything that didn't make it). New preload pair onBeforeQuitFlush /
  beforeQuitFlushDone (typed in index.d.ts).
- Safety: 30s per-task timer, re-armed on every markPending.

`isImmediateOp` (bypass batching): is_archived, is_in_my_day, completion — done-status looked up
synchronously in statusStore, with `completed_date` string as fallback proxy when the status isn't hydrated
(cross-project views). On an immediate push the pending mark is CANCELLED, not flushed — the push carries
the full task row so buffered edits ride along; flushing later would be a redundant duplicate.
deleteTask/bulkDeleteTasks also cancelPending (tombstone already pushed).

GOTCHA worth remembering: two CONCURRENT dynamic `import()`s of the same vi.mock'ed module inside Vitest can
race — the second resolves to the REAL module, not the mock (hit in flushAll's Promise.all; sequential
flushes were fine). Fixed by caching the module promise once (`getStoreModule()`), which is also what
production wants anyway. If a future service does `await import(...)` per concurrent call and its tests
flake with "mock not applied", this is why.

Debounce interplay (intentional, no data loss): title/description keep their 1s debounce; if Escape closes
the panel inside that window, the debounced updateTask fires AFTER close → openTaskId is null → pushes
immediately. One push either way.

Tests: +10 TaskBatchSyncManager (markPending idempotent/timer re-arm/30s flush, flush clears+skips-deleted,
double-flush no-op, flushAll drains, cancelPending disarms). 899 tests green, typecheck clean, dev compiles
on :5200.

## Story #94 — Remove password login for OAuth users (Edge Function with service_role) (2026-06-10)

Third leg of the password story (#65 shipped Add/Change): a Google-OAuth user who previously added a
password can now remove it again from Settings → Profile → Password and revert to Google-only sign-in.
Needs the admin API (no client-side way to clear encrypted_password), so it ships as a new
supabase/functions/remove-password edge function.

Edge function follows the story-#88/#93 extraction pattern: core logic in dependency-free
removePassword.ts (structural RemovePasswordClient interface, no npm:/Deno imports → vitest-testable),
index.ts is a thin Deno.serve wrapper modeled on send-password-reset (same CORS + admin client; adds
Content-Type: application/json so functions.invoke parses the body). Contract: missing/invalid Bearer →
401; user without a non-email identity → 200 {ok:false, error:'no_oauth_identity'} (200 on purpose —
non-2xx surfaces to invoke() as an opaque FunctionsHttpError, the renderer wants to read the body);
otherwise updateUserById(id, {password: null}) then {user_metadata:{has_password:false}} → {ok:true}.
Admin-call failures → 500 with the message, metadata write skipped if the password clear failed.
supabase-js types password as string|undefined, so the wrapper casts through the structural interface —
GoTrue's admin endpoint accepts the explicit null (per the audited story).

Renderer: extracted identity detection into features/settings/identityFlags.ts —
deriveIdentityFlags(user) ORs the email identity with the has_password metadata flag (OAuth users who add
a password never gain an 'email' identity; flag set by handlePasswordSave, cleared by the edge function,
so add → remove → add round-trips), plus canRemovePasswordLogin() encoding the visibility rule
(hasEmailIdentity && hasOAuthIdentity — never offer to strip the only sign-in method).
ProfileSettingsContent now uses the utility and conditionally renders the new RemovePasswordSection
component (kept separate — the parent is already over the 150-line rule): danger button per the
Forget-Saved-Login pattern, persistent confirm toast (Remove danger / Cancel muted), invoke with explicit
Bearer header, on success clearCredentials() (wipes Keychain + saved email — existing IPC, no new bridge
method) + refreshSavedLogin() + setHasEmailIdentity(false) so the section flips back to "Add Password
Login" without a reload.

DEVIATION (cosmetic): the story said surface failures in the parent's passwordError; the section shows
its own error line directly under the Remove button instead — same visual treatment, better proximity
(passwordError renders inside the change-password form, far from the Remove button).

Tests: +13 in removePassword.test.ts (401 missing header / non-Bearer / bad JWT; jwt extraction;
email-only and no-identities rejected without admin calls; happy path asserts both updateUserById payloads
in order; first/second admin failure → 500), +10 in identityFlags.test.ts (flag matrix incl. has_password
round-trip, missing/null identities; canRemovePasswordLogin truth table). 929 tests green (55 files),
