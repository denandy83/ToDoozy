## 2026-06-10 — Story #91: Expand Realtime coverage (per-user channel + activity_log + task_labels)

Implemented all four parts:
1. **Per-user channel** — new `UserChannelService.ts`: stable channel `user:${userId}` with filtered subs on
   project_members / user_labels / user_saved_views / user_project_areas. Membership INSERT pulls the project
   down (shared → syncProjectDown+subscribeToProject; personal → projects descriptor applyRemote + addMember +
   pullNewTasks + personal channel, distinguished by remote member count). Membership DELETE removes the project
   locally + tears down its channel; the ACTIVE shared project is excluded (AppLayout's dialog owns that case).
   Reconnect/backoff mirrors the personal channels (suspend/online gates, joined auto-rejoin guard, give-up →
   connectionLost banner); pause/force are invoked from PersonalSyncService's pauseReconnectsForSuspend /
   forceReconnectAllPersonal so powerMonitor resume, the online listener, and SessionBanner retry all cover it.

   isOffline flip in finishSessionRecovery re-runs it, same as the project channels.
2. **activity_log on personal channels** — INSERT sub per personal project; new IPC `activityLog:applyRemote`
   (INSERT OR IGNORE by id, preserves remote created_at, seeds placeholder users, returns
   applied/duplicate/missing-task). One 2.5s retry covers the activity-before-task Realtime race. Detail panel
   refresh via new `taskStore.activityRefresh` counter + `bumpActivityRefresh` (DetailActivityLog re-fetches on
   bump). ALSO wired the shared channel's 'activity' events in AppLayout — they were being dropped on the floor
   (remote members' activity never reached local SQLite live).
3. **task_labels targeted pull (option a)** — root cause confirmed: the MCP edge fn's addLabel/removeLabel

   treats the task as touched. Fix: every personal-channel tasks INSERT/UPDATE triggers
   `pullTaskLabelsForTask(taskId)` (O(1) fetch .eq('task_id')) → new `tasks:applyRemoteTaskLabels` IPC.

   Extracted `ensureLabelsExistLocally()` from pullNewTasks (shared by both paths).
4. **Polling safety net** — `pullActivityLogForProject` in syncTables.ts: pull-only incremental sweep cursored on

## Story #92 — Batch task-detail edits (2026-06-10)

New `TaskBatchSyncManager.ts`: module-level `pendingTaskIds` Set + per-task 30s safety timers. While a task
is open in the Detail panel, `taskStore.updateTask` / `addLabel` / `removeLabel` call `markPending(taskId)`
instead of pushing; `flush(taskId)` re-reads the task from the store and pushes through the SAME
`syncIfShared` routing (now exported from taskStore) so shared/personal both work. `flush` is a no-op when
not pending (double-flush safe) and skips tasks deleted while buffered.

Boundaries wired:
- Task switch: `selectTask`/`navigateTask`/`setCurrentTask(id)` flush the previous lastSelectedTaskId.
- Panel close: `setCurrentTask(null)` + `clearSelection` flushAll; DetailPanel's Escape handler (which
  bypasses store actions with a raw setState) flushes explicitly.
- App blur: window 'blur' listener in App.tsx.
- Quit: main intercepts the FIRST before-quit (preventDefault), sends `app:before-quit-flush` to all
  windows, renderer flushes and acks via `app:before-quit-flush-done`, main quits on ack or 1.5s timeout
  (sync_queue/reconcile covers anything that didn't make it). New preload pair onBeforeQuitFlush /
  beforeQuitFlushDone (typed in index.d.ts).
- Safety: 30s per-task timer, re-armed on every markPending.

`isImmediateOp` (bypass batching): is_archived, is_in_my_day, completion — done-status looked up
synchronously in statusStore, with `completed_date` string as fallback proxy when the status isn't hydrated
(cross-project views). On an immediate push the pending mark is CANCELLED, not flushed — the push carries
the full task row so buffered edits ride along; flushing later would be a redundant duplicate.
deleteTask/bulkDeleteTasks also cancelPending (tombstone already pushed).

GOTCHA worth remembering: two CONCURRENT dynamic `import()`s of the same vi.mock'ed module inside Vitest can
race — the second resolves to the REAL module, not the mock (hit in flushAll's Promise.all; sequential
flushes were fine). Fixed by caching the module promise once (`getStoreModule()`), which is also what
production wants anyway. If a future service does `await import(...)` per concurrent call and its tests
flake with "mock not applied", this is why.

Debounce interplay (intentional, no data loss): title/description keep their 1s debounce; if Escape closes
the panel inside that window, the debounced updateTask fires AFTER close → openTaskId is null → pushes
immediately. One push either way.

Tests: +10 TaskBatchSyncManager (markPending idempotent/timer re-arm/30s flush, flush clears+skips-deleted,
double-flush no-op, flushAll drains, cancelPending disarms). 899 tests green, typecheck clean, dev compiles
on :5200.
