## Story #76 — bare "121s" / "5m" / "3d" tokens falsely set a date
- Root cause: parseNlpDate uses chrono's casual parser (chrono.parse), which has a relative-duration parser that reads a bare NNs/NNm/NNh/NNd/NNw/NNy token as "NN <unit> from now". In multi-word task names ("fix bug 121s", "migrate data 2w") the 80% match-coverage filter in useSmartInput doesn't fire, so the chip appears and the due date is applied on submit.
- Fix (src/shared/nlpDateParser.ts): after each chrono.parse result (both the normalized-text branch and the original-text branch), reject when the matched text is a bare relative-duration abbreviation — `if (/^\d+[smhdwy]$/i.test(r.text.trim())) return null`. The regex only matches single-token abbreviations: it does NOT match "3pm"/"9am" (2-char suffix), "in 5m"/"in 2h" (matched text includes "in "), "tomorrow"/"next friday" (no digit prefix), or "0.5h" (decimal). So intentional relative durations via "in 5m"/"in 121s" still parse.
- Tests: added 9 cases to nlpDateParser.test.ts — no false positive for 121s/5m/2h/3d/2w/2y; still parses "in 5m"/"in 121s"/"tomorrow". nlpDateParser file: 28 tests pass. Full suite 796 pass / 42 files (was 787). typecheck clean. dev compiles + serves on :5200 (DB-open warning is the usual unrelated env/path noise).
